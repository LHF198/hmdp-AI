# 秒杀下单方案演进记录（学习材料）

> 本文档记录了 `VoucherOrderServiceImpl.seckillVoucher` 从单机锁到 Redis Stream 异步化的完整演进史。
> 历史实现曾以注释形式保留在服务类中（约 300 行），为提升可读性已归档于此。
> 阅读建议：按 版本一 → 版本五 顺序阅读，重点关注每个版本**解决了什么问题、引入了什么新问题**。

## 版本一：synchronized 本地锁（单机可用）

```java
@Transactional
public Result createVoucherOrder(Long voucherId) {
    // 5.一人一单
    Long userId = UserHolder.getUser().getId();

    // 本地锁：同一 JVM 内保证同用户串行
    synchronized (userId.toString().intern()) {
        // 1.查询订单，判断是否已购买（count > 0 则拒绝）
        // 2.扣减库存（update ... set stock = stock - 1 where id = ? and stock > 0）
        // 3.创建订单（save）
    }
}
```

**问题**：
- 锁是 JVM 进程内的，**集群部署（多实例）时锁失效**，无法保证一人一单
- `intern()` 字符串常量池有内存泄漏风险
- 校验 + 扣库存 + 建单非原子，高并发下可能出现超卖

**演进动机**：锁必须存到所有实例共享的地方 → Redis。

## 版本二：SimpleRedisLock 手写分布式锁（SETNX + Lua 释放）

```java
SimpleRedisLock redisLock = new SimpleRedisLock("order:" + userId, stringRedisTemplate);
boolean isLock = redisLock.tryLock(1200); // 超时时间 1200ms
if (!isLock) {
    return Result.fail("不允许重复下单！");
}
try {
    // ... 一人一单校验 + 扣库存 + 建单（@Transactional 包住）
} finally {
    redisLock.unlock();
}
```

**原理**（`utils/SimpleRedisLock.java` 仍在项目中，可对照阅读）：
- 加锁：`SET lock:order:{userId} {threadId} NX EX {ttl}`——NX 保证互斥，EX 防死锁
- 释放：Lua 脚本先 `get` 校验锁持有者（value 为当前线程标记）再 `del`，**防止误删他人锁**（锁超时后旧锁被他人获取的场景）

**问题**：
- 不可重入：同一线程嵌套加锁会死锁
- 超时时间写死：业务执行超过 TTL 时锁提前释放，并发安全被破坏（无法自动续期）

**演进动机**：需要"可重入 + 自动续期"的成熟实现 → Redisson。

## 版本三：Redisson 分布式锁（可重入 + 看门狗）

```java
RLock redisLock = redissonClient.getLock("lock:order:" + userId);
boolean isLock = redisLock.tryLock();
if (!isLock) {
    return Result.fail("不允许重复下单！");
}
try {
    // ... 一人一单校验 + 扣库存 + 建单（@Transactional 包住）
} finally {
    redisLock.unlock(); // Redisson 内部校验持有者，不会误删他人锁
}
```

**改进**：
- **可重入**：同线程可多次加锁（Hash 结构记录次数）
- **看门狗自动续期**：默认 30s 锁超时，业务未完成时后台线程每 10s 续期，业务完成释放后停止

**问题**：
- 整个"校验 + 扣库存 + 建单"仍走**同步链路**，高峰期数据库压力大
- 每单一次事务提交，吞吐受限于 DB 写能力

**演进动机**：把下单从"同步写库"改为"先确认资格、再异步落库" → 消息队列。

## 版本四：Lua 原子校验 + BlockingQueue 异步下单（内存队列）

```java
// Lua 脚本：库存/一人一单/时间窗一次原子判定，返回 0 成功 / 1 库存不足 / 2 重复下单
Long result = stringRedisTemplate.execute(SECKILL_SCRIPT, Collections.emptyList(), voucherId, userId);
if (r != 0) { return Result.fail(...); }

// 有资格：构造订单放入 JVM 内存阻塞队列
orderTasks.add(voucherOrder);

// 后台线程池消费
private class VoucherOrderHandler implements Runnable {
    public void run() {
        while (true) {
            VoucherOrder voucherOrder = orderTasks.take(); // 阻塞获取
            createVoucherOrder(voucherOrder);              // 异步落库
        }
    }
}
```

**改进**：
- Lua 脚本把"库存判断 + 扣减 + 一人一单标记"收敛为一次 Redis 原子操作，**秒杀资格确认 O(1)**
- 落库从同步改为异步，接口只返回"抢购成功"，大幅提升吞吐

**问题**：
- BlockingQueue 在 **JVM 内存**中：应用重启/宕机丢消息；多实例各自为政，无法水平扩容消费

**演进动机**：需要"进程外、可持久化、支持消费组"的消息队列 → Redis Stream。

## 版本五（当前）：Lua + Redis Stream 异步下单（生产形态）

```java
// 1. Lua 原子校验（返回码语义见 SeckillConstants，与 seckill.lua return 值一一对应）
//    0 成功并已 XADD 到 stream.orders；1/2/3/4 分别对应库存不足/重复下单/未开始/已结束
// 2. 后台线程 XREADGROUP 消费（g1 消费组，批量拉取 10 条/次，BLOCK 2s）
// 3. 编程式事务落库（TransactionTemplate），失败进入 pending 列表兜底重试
// 4. 单条消息失败超 MAX_PENDING_RETRY 次 → 移入死信队列 stream.orders.dlq
// 5. daemon 线程池 + @PreDestroy shutdownNow 优雅停机
```

**相对版本四的强化**：

| 能力 | 版本四 | 版本五 |
|---|---|---|
| 消息持久化 | ❌ JVM 内存，重启即丢 | ✅ Redis Stream 落盘 |
| 消费扩容 | ❌ 单实例内存队列 | ✅ 消费组多消费者（多实例） |
| 故障兜底 | ❌ 失败即丢 | ✅ pending 重试 + 死信队列 |

## 关键设计要点（面试/复习自检）

1. **为什么 Lua 脚本能保证原子性？** Redis 单线程执行脚本，脚本内所有命令要么全部执行、要么全部不执行，天然串行。
2. **为什么消费端还要再加 Redisson 锁？** Lua 只保证了"资格校验"原子，消费端"查单 + 扣库存 + 建单"是数据库操作，多消费者可能并发处理同一用户消息，需要 `lock:order:{userId}` 锁保证一人一单落库。
3. **为什么用编程式事务而不是 @Transactional？** 消费线程是自定义线程池启动的，`createVoucherOrder` 若带 @Transactional 注解会被 **Spring 代理自调用失效**（同类内部调用不经过代理）；同时业务失败不抛异常（返回 false 确认丢弃），事务边界需要手动控制。
4. **为什么 Stream 消费异常要分"整批"和"单条"两级处理？** 批拉取时单条失败会中断整批，此时从 pending-list（ReadOffset 0）逐条重放兜底，避免坏消息阻塞流水线。
5. **为什么线程池要用 daemon？** 非 daemon 线程会阻止 JVM 退出，Spring 销毁 Redis 连接工厂后消费线程仍在 while(true) 循环，导致 "LettuceConnectionFactory was destroyed" 刷屏与僵尸进程。
