## 第 1 章（入门）：整体架构与一次请求的完整旅程

### 1.1 架构图

```
浏览器
  │  http://localhost:8080
  ▼
nginx ──静态──► html/dist/app（Vue SPA 产物）
  │
  ├─ /api/**    ──剥离前缀──► Spring Boot :8081 ──► MySQL / Redis
  └─ /api/ai/** ──保留前缀──► Spring Boot :8081（AI 流式接口，关闭缓冲）
```

要点：**开发和生产的请求路径语义严格一致**——Vite dev 代理（`frontend/vite.config.js:61-73`）与 nginx 配置（`frontend/conf/nginx.conf:86-97`）行为对齐，换环境不改代码。

### 1.2 后端分层（经典三层 + 工具层）

```
controller/   接收请求、参数校验、返回统一 Result
service/      业务逻辑（接口 I*Service + impl/*ServiceImpl）
mapper/       MyBatis-Plus 数据访问（单表 CRUD 零 XML）
entity/ dto/  数据库实体 / 传输对象
utils/        横切能力：CacheClient、RedisIdWorker、UserHolder、拦截器
config/       装配：MvcConfig（拦截器注册）、RedissonConfig、MybatisConfig
```

### 1.3 统一返回体与前后端契约

所有 Controller 返回 `Result`（`dto/Result.java`）：`{success, data, errorMsg}`。前端 `http.js` 响应拦截器统一解包：成功返回数据，失败 reject 错误信息。这就是"前后端契约"——**约定一次，处处受益**，业务代码里再不写错误处理样板。

### 1.4 一次请求的完整旅程（以"查看商铺详情"为例）

```
GET /shop/1
  → RefreshTokenInterceptor（order=0）：解析 token → 查 Redis → 存 ThreadLocal → 滑动续期
  → LoginInterceptor（order=1）：有 @Anonymous？有登录用户？否则 401
  → ShopController → ShopServiceImpl
  → CacheClient.queryWithPassThrough("cache:shop:1", ...)：先 Redis 后 MySQL
  → Result.ok(shop) → JSON 响应
  → afterCompletion：UserHolder.removeUser() 清理 ThreadLocal
```

## 第 2 章（入门）：数据库设计与 MyBatis-Plus 分层

### 2.1 十张表与关系主线（`src/main/resources/db/hmdp.sql`）

```
tb_user ──1:n── tb_blog ──n:1── tb_shop ──n:1── tb_shop_type
   │                                │
   │                                └─1:n── tb_voucher ──1:1── tb_seckill_voucher
   │                                          │
   └──────────1:n── tb_voucher_order ◄────────┘
tb_user_info（用户资料 1:1）  tb_follow（关注关系）  tb_blog_comments（二级评论）
```

设计要点，全是考点：

- **逻辑外键**：没有任何物理 FOREIGN KEY。互联网项目惯例——外键约束在高并发写入时是负担，一致性由代码保证。
- **唯一索引兜底并发**：`tb_voucher_order.uk_user_voucher(user_id, voucher_id)` 用数据库唯一约束实现"一人一单"的最终防线；`tb_follow.uk_user_follow` 防重复关注。代码捕获 `DuplicateKeyException` 视为幂等成功（`FollowServiceImpl.java:57-61`）。
- **金额/评分用整数**：`tb_voucher` 金额单位为分、`tb_shop.score` 乘 10 存储——**坚决不用浮点数存钱**（浮点精度问题），展示层再换算（`MoneyUtils.fenToYuan`）。
- **高频关系数据放 Redis**：点赞、共同关注、Feed 不进 SQL，放 Redis 的 ZSet/Set（见第 5 章）。
- 另有 `db/migration_v2_db_optimize.sql` 记录索引优化演进，可对照学习"索引为何这样建"。

### 2.2 MyBatis-Plus 的使用范式

- Mapper 接口继承 `BaseMapper<Entity>` 即获得全部单表 CRUD；
- Service 继承 `ServiceImpl<Mapper, Entity>` 获得 `lambdaQuery()` / `lambdaUpdate()` 链式查询；
- 复杂 SQL（如商户查券）才写 XML（`mapper/VoucherMapper.xml`）。

原则：**单表操作零 XML，多表/复杂 SQL 才下沉到 Mapper XML**。

## 第 3 章（进阶）：登录认证——双拦截器、ThreadLocal 与 Redis 会话

> 问题引入：为什么不用 HttpSession？集群部署时 Session 存在哪？登录态如何"用着就不过期"？

### 3.1 短信验证码登录流程（`service/impl/UserServiceImpl.java`）

1. **发验证码**（`sendCode`，第 74-95 行）：校验手机号 → 若 `login:code:{phone}` 还有未消费的验证码则拒绝重发（TTL 即冷却窗口，省一个 key）→ 生成 6 位验证码 `SET login:code:{phone} code EX 120`。
2. **登录**（`loginByCode`，第 123-142 行）：比对验证码，**校验通过立即删除**防止 TTL 内复用；用户不存在则自动注册（唯一索引 + `DuplicateKeyException` 兜底并发注册）。
3. **密码登录**（`loginByPassword`，第 147-185 行）：失败计数 `login:fail:{phone}`（INCR，首失败设 10 分钟窗口），≥5 次锁定；密码用 BCrypt 校验。
4. **签发登录态**（`doLogin`，第 190-209 行）：

```java
String token = UUID.randomUUID().toString(true);          // token 即 Redis key 的一部分
UserDTO userDTO = BeanUtil.copyProperties(user, UserDTO.class);  // 脱敏：只留 id/nickName/icon
stringRedisTemplate.opsForHash().putAll("login:token:" + token, userMap);
stringRedisTemplate.expire(tokenKey, LOGIN_USER_TTL, MINUTES);
return Result.ok(token);
```

**为什么不用 HttpSession**：token 即 key、用户数据存 Redis Hash，天然支持多实例集群（任何一台机器都能验）；只存 `UserDTO` 脱敏；登出 = 删 key，立即可失效。

### 3.2 双拦截器机制（`config/MvcConfig.java:20-30`）

两个拦截器都拦 `/**`，靠 `order` 串成流水线：

| 拦截器 | order | 职责 | 拦截决策 |
|---|---|---|---|
| `RefreshTokenInterceptor` | 0 | 解析 token → 查 Redis → 存 ThreadLocal → **刷新 TTL（滑动过期）** | 永远放行 |
| `LoginInterceptor` | 1 | 鉴权：无用户且无 `@Anonymous` → 401 | 默认拒绝 + 注解显式放行 |

精妙之处：

- **职责分离**：第一个只管"有没有用户都试试解析并续期"，所以匿名接口（如博客列表）也能拿到登录用户信息来渲染"我是否点赞"；第二个只管"这个接口要不要登录"。
- **`@Anonymous` 注解驱动**（`annotation/Anonymous.java`）：新接口默认要求登录，想匿名必须显式标注。相比在配置里维护 `excludePathPatterns` 白名单，**默认安全**，不会因 URL 匹配疏漏漏鉴权（`utils/LoginInterceptor.java:29-48`）。
- **滑动过期**：每次请求都 `expire` 续期，活跃用户永不过期、闲置用户到期回收——这就是"用着就不过期"。

### 3.3 ThreadLocal：同一线程的"全局变量"（`utils/UserHolder.java`）

```java
private static final ThreadLocal<UserDTO> tl = new ThreadLocal<>();
```

- **为什么用它**：Tomcat 每个请求一个线程，ThreadLocal 让同一线程内任意层（Controller/Service/工具类）都能取到当前用户，免传参；不同请求线程互不干扰。
- **为什么必须 remove**：Tomcat 线程**池化复用**，不清除会导致下一个复用该线程的请求读到上一个用户——"串号"事故。清除点在 `RefreshTokenInterceptor.afterCompletion`（谁写入谁负责清）。

## 第 4 章（进阶）：Redis 缓存三大经典问题——穿透、击穿、雪崩

> 问题引入：直接"先查缓存、没有再查库、回填缓存"看似简单，生产上会踩哪三个坑？

核心封装在 `utils/CacheClient.java`，类注释（第 26-33 行）即设计总纲：穿透用空值占位，击穿用互斥锁或逻辑过期，**雪崩不在此类解决**（由调用方给不同 key 传差异化 TTL）。

### 4.1 缓存穿透：把"不存在"也缓存（`queryWithPassThrough`，第 83-112 行）

恶意请求不断查不存在的 id，每次都穿透缓存打到数据库。解法：

```java
String json = redis.get(key);
if (StrUtil.isNotBlank(json)) return toBean(json);   // 命中真实数据
if (json != null) return null;                       // 命中空值占位 → 直接返回，不查库！
R r = dbFallback.apply(id);                          // 未命中才查库
if (r == null) { redis.set(key, "", 2分钟); return null; }  // 缓存空值（短 TTL）
this.set(key, r, time, unit);
```

`isNotBlank` 与 `!= null` 两个分支区分三种状态：真实数据 / 空值占位 / key 不存在。空值 TTL 只给 2 分钟——既挡住攻击，又不长期占用内存、不妨碍该 id 真实数据后续生效。

### 4.2 缓存击穿（热点 key 重建）：两种方案对比

热点 key 过期瞬间，万级并发同时发现缓存失效、同时去查库重建 → 数据库雪崩。两种解法：

**方案 A：互斥锁（`queryWithMutex`，第 160-215 行）**——只放行一个线程重建，其余等待：

```java
while (lockValue == null && retry < 20) {      // 最多重试 20×50ms ≈ 1s
    lockValue = tryLock("lock:shop:" + id);    // SET key UUID NX EX 10
    if (lockValue == null) Thread.sleep(50);
}
try { r = dbFallback.apply(id); this.set(key, r, ...); }
finally { if (lockValue != null) unlock(lockKey, lockValue); }  // 仅持有者才释放
```

工程改进：循环重试替代递归（防栈溢出）；设重试上限，超时降级为直接查库，**保证可用性而非无限自旋**。

**方案 B：逻辑过期（`queryWithLogicalExpire`，第 114-158 行）**——key 永不物理过期，过期时间存 value 里（`RedisData{data, expireTime}`）：

```java
if (StrUtil.isBlank(json)) return null;         // 要求提前预热，未命中不查库
if (expireTime.isAfter(now)) return r;          // 未逻辑过期
if (tryLock(...) != null) {
    CACHE_REBUILD_EXECUTOR.submit(() -> { ...重建... });  // 异步线程池重建
}
return r;                                       // 永远立即返回（可能是旧数据）
```

**对比表（面试高频）**：

| 维度 | 互斥锁 | 逻辑过期 |
|---|---|---|
| 一致性 | 强（等待新数据） | 弱（短期返回旧数据，最终一致） |
| 延迟 | 有等待 | 零等待 |
| 内存 | 正常 | key 永不过期，占用偏高 |
| 前置条件 | 无 | 必须数据预热 |
| 实现复杂度 | 低 | 高（额外线程池） |

### 4.3 缓存雪崩

大量 key 同时过期 → 集体穿透。本项目解法朴素有效：**给每个 key 的 TTL 加随机扰动**（调用方传差异化 TTL），避免同一时刻集体失效。

## 第 5 章（进阶）：Redis 数据结构的业务应用——点赞、关注、签到、Feed

> 问题引入：Redis 不只是"缓存字符串"。五种数据结构各适合什么业务？

### 5.1 全局唯一 ID（`utils/RedisIdWorker.java:28-42`）

自研雪花式 64 位 ID：

```
| 高 32 位：秒级时间戳（相对 2022-01-01，约可用 69 年） | 低 32 位：当日自增序列 |
```

```java
long count = redis.increment("icr:" + keyPrefix + ":" + 当天日期);  // INCR 原子，集群安全
return timestamp << 32 | count;
```

妙处：序列号 key 带日期 → 每天从 0 重计（单日上限 42 亿），且**天然支持按天统计单量**；时间戳在高位 → ID 单调递增，对 B+ 树索引友好（避免页分裂）。

### 5.2 点赞：为什么用 ZSet 不用 Set（`BlogServiceImpl.likeBlog`，第 192-236 行）

- `ZADD blog:liked:{blogId} userId 当前时间戳`——score 存时间戳，既能 O(1) 判是否已赞（`ZSCORE`），又能按时间排序输出"最早点赞榜 Top5"（`ZRANGE key 0 4`）。
- 点赞榜查用户用 `WHERE id IN (...) ORDER BY FIELD(id, ...)` 保序——IN 查询会乱序，`FIELD` 修正。
- **DB/Redis 一致性**：先 DB 计数 +1，再写 ZSet；Redis 写失败回滚 DB 计数（第 206-214 行）——"先 DB 后缓存 + 失败回滚"实用范式。

### 5.3 关注与共同关注：Set 的妙用（`FollowServiceImpl`）

- 关注关系双写：DB 表 + `follows:{userId}` Set（我关注的人）。
- **共同关注 = `SINTER follows:{我} follows:{对方}` 一行交集**（第 95 行）。把关系计算从 SQL 多表 JOIN 挪到 Redis 内存集合运算，毫秒级。

### 5.4 签到：Bitmap 的极致压缩（`UserServiceImpl.sign`，第 240-295 行）

`SETBIT sign:{userId}:{yyyyMM} (当天-1) 1`——一个月的签到只占 **31 个 bit（4 字节）**。统计连续签到用 `BITFIELD GET u{n} 0` 取回后做末位与运算循环。Bitmap 是"布尔序列"场景的神器。

### 5.5 Feed 流：推模式（写扩散）+ 滚动分页（`BlogServiceImpl`）

**推**（`saveBlog`，第 260-291 行）：笔记发布后，异步线程池把笔记 id `ZADD feed:{粉丝id} blogId 时间戳` 推进每个粉丝的收件箱。为什么异步？大 V 粉丝多时同步推会阻塞发布接口。

**拉**（`queryBlogOfFollow`，第 367-412 行）：滚动分页替代传统 `LIMIT offset,size`：

```
ZREVRANGEBYSCORE feed:{userId} max 0 LIMIT offset 2
```

为什么不用偏移分页？Feed 是动态插入的——用户翻页期间新笔记插入头部，偏移分页会重复/漏读。滚动分页改用"上次最后一条的 score 作为本次上限 max"，并处理同分重复（score 相同则 offset++，否则重置为 1，第 383-395 行——细节中的魔鬼）。

**删除的善后**（`deleteBlog`，第 295-364 行）：DB 删除在事务内，Redis 清理（点赞缓存、所有粉丝收件箱里的该笔记）**延后到事务提交后**（`afterCommit`）——防止 DB 回滚但缓存已删的不可逆副作用。

## 第 6 章（高级）：优惠券秒杀——Lua、Stream 消息队列与多重防线

> 问题引入：1 万张券、100 万人抢。数据库行锁扛不住怎么办？答案：**把高并发判定挡在 Redis 内存里（Lua 原子），把慢速落库异步化（Stream 队列），数据库只做最终兜底**。

### 6.1 全链路图

```
POST /voucher-order/seckill/{id}
  └─ VoucherOrderServiceImpl.seckillVoucher()（VoucherOrderServiceImpl.java:372）
       ├─ RedisIdWorker 生成订单号
       ├─ 执行 seckill.lua：时间窗→库存→一人一单→扣库存→记用户→XADD 投递 Stream
       └─ 立即返回 orderId（此时订单还没落库！前端轮询或后续查询确认）
异步消费（daemon 单线程，VoucherOrderServiceImpl.java:207）
  ├─ XREADGROUP g1 批量拉 10 条 → createVoucherOrder() 落库 → XACK
  ├─ 失败 → handlePendingList() 重读 pending 重试
  └─ 同一消息失败 3 次 → 死信队列 stream.orders.dlq
```

### 6.2 第一道防线：seckill.lua 原子判定（`src/main/resources/seckill.lua`）

Lua 脚本在 Redis 单线程内执行，**执行期间不插入其他命令，天然原子**——竞态从根上消失：

```lua
-- 时间窗（用 Redis 服务器自己的时钟，避免应用服务器时钟不一致）
if(nowTime < beginTime) then return 3 end
-- 库存
if(stock <= 0) then return 1 end
-- 一人一单（Set 成员判断）
if(redis.call('sismember', orderKey, userId) == 1) then return 2 end
-- 全部通过：扣库存 + 记用户 + 投递消息，三步原子完成
redis.call('incrby', stockKey, -1)
redis.call('sadd', orderKey, userId)
redis.call('xadd', 'stream.orders', '*', 'userId', userId, 'voucherId', voucherId, 'id', orderId)
return 0
```

关键理解：**"判断 + 扣减"在同一个原子区内**，不存在"两个请求同时读到 stock=1 都通过"的 check-then-act 竞态。这是秒杀系统的第一道也是最快的一道防线。返回码集中定义在 `SeckillConstants.java:14-25`，注释要求改脚本必须同步该类——防两端语义漂移。

**前置数据准备**：新增秒杀券时在事务 `afterCommit` 回调里写 Redis（`VoucherServiceImpl.java:117-124`，防"Redis 已写、DB 回滚"脏数据）；应用启动时预热库存/下单集合/时间窗（`initSeckillCache`，第 56-85 行，防 Redis 重启后重复下单）。

### 6.3 第二道防线：Stream 消费者组的可靠性

为什么用 Stream 而不是 List 队列或内存阻塞队列？——**ACK + pending 列表**：

- `XREADGROUP ... STREAMS stream.orders >`：`>` 只读未投递过的新消息；
- 处理成功才 `XACK`；消费者崩溃时，未 ACK 的消息留在 **pending 列表**，重启后重读补偿——**at-least-once 语义，不丢单**；
- 坏消息熔断：重试 3 次进死信队列，防止单条坏消息卡死流水线（`handlePendingList`/`moveToDlq`，第 243-308 行）。

代价：消息可能重复投递，**消费端必须幂等**——正好由第三道防线保证。

### 6.4 第三道防线：DB 兜底（`createVoucherOrder`，第 311-370 行）

Lua 保证 Redis 状态正确，但 **DB 才是最终事实**（Redis 数据丢失、消息重投都可能绕过第一层）：

```java
RLock lock = redissonClient.getLock("lock:order:" + userId);  // 锁粒度=用户，并发度最大化
lock.tryLock(1, SECONDS);
// 编程式事务内：
Long count = count(...user_id=? and voucher_id=?);   // ① DB 查重（一人一单兜底）
if (count > 0) return false;
boolean ok = seckillVoucherService.lambdaUpdate()
    .setSql("stock = stock - 1")
    .eq(voucher_id, ...).gt(stock, 0)                // ② 乐观锁：WHERE stock > 0
    .update();
save(voucherOrder);                                   // ③ 建单（唯一索引最后兜底）
```

- **防超卖**：`UPDATE ... SET stock=stock-1 WHERE stock>0` 把判断下推到 SQL WHERE，靠 InnoDB 行锁实现 CAS 式乐观锁，避免"先查后改"竞态。
- **事务**：扣库存 + 建单在编程式事务（`TransactionTemplate`）内，任一失败整体回滚。
- 业务失败（已买过）静默 ACK 丢弃；锁失败/中断**抛异常让消息回 pending 重试**——区分"业务失败"和"系统失败"是消息消费的关键设计。

**双重校验哲学**：Lua 层是"快速拒绝"（性能），DB 层是"最终正确"（可靠）。任何单一层都不完整。

## 第 7 章（高级）：分布式锁——手写锁、unlock.lua 与 Redisson

本项目两套锁方案并存，正好对比学习。

### 7.1 手写锁 + unlock.lua（`CacheClient.java:223-239`）

加锁：`SET lock:shop:{id} {uuid} NX EX 10`——value 存 UUID 持有者标识。为什么 value 不能随便写？

**误删问题**：线程 A 持锁执行中锁过期 → 线程 B 获得锁 → A 执行完直接 `DEL`，删掉的是 B 的锁。所以要"先比较持有者再删"——但 `GET` + `DEL` 两条命令之间仍有竞态（比较完锁恰好过期易主）。解法是 Lua 原子化（`src/main/resources/unlock.lua`）：

```lua
if(redis.call('get', KEYS[1]) == ARGV[1]) then
    return redis.call('del', KEYS[1])   -- 标识一致才删
end
return 0
```

### 7.2 Redisson（`config/RedissonConfig.java:31-41`）

秒杀下单用的就是 Redisson（`VoucherOrderServiceImpl.java:315`）。相比手写 SETNX：

| 能力 | 手写锁 | Redisson |
|---|---|---|
| 可重入 | 无 | 同线程重入计数 |
| 锁续期 | 固定 TTL，业务超时即丢锁 | 看门狗：默认 30s 租约，持有期间每 10s 自动续期 |
| 等待方式 | 自旋轮询（费 CPU） | pub/sub 订阅唤醒 |
| 释放安全 | 需 Lua 比对标识 | `isHeldByCurrentThread()` 内置判断 |

> 自检：Redisson 看门狗解决了手写锁的哪个具体风险？如果 Redis 主从切换时锁信息还没同步到从库，两套方案各自会怎样？（引申：RedLock 之争，可拓展阅读）

## 第 8 章（高级）：AI 探店助手——Spring AI、RAG、Function Calling 与优雅降级

> 问题引入：怎么让大模型回答"推荐附近好吃的火锅店"这种需要**实时真实数据**的问题？怎么让没配 API key 的开发机也能正常启动？

### 8.1 整体链路

```
GET /api/ai/chat/stream?message=...&conversationId=...
  → AiRateLimitInterceptor（IP 限流 30 次/分钟，Redis 固定窗口）
  → ChatController → AssistantService.chatStream()
  → ChatClient（系统提示词 + 三件套）
      ├─ MessageChatMemoryAdvisor → RedisChatMemory（多轮上下文记忆）
      ├─ QuestionAnswerAdvisor   → SimpleVectorStore（RAG 检索知识库）
      └─ ShopQueryTool           → JdbcTemplate 实时查库（Function Calling）
  → DashScope（qwen-flash）→ Flux<String> 逐字流式返回
```

核心装配在 `ai/config/AiConfig.java:71-92`：读取 `prompts/system-prompt.st`（角色设定："AI 探店助手，先调工具查真实数据，绝不编造店铺信息"），链式挂上记忆 Advisor、RAG Advisor 和工具。

### 8.2 三大能力各解决什么

**RAG（检索增强生成）**，`ai/config/RagConfig.java:62-124`：把 `knowledge/店铺信息.md` 切分（`TokenTextSplitter`）→ 向量化（text-embedding-v4）→ 存内存 `SimpleVectorStore`；问答时先按相似度检索（topK=3、阈值 0.5）把相关片段塞进提示词。**解决"模型不知道你的私有知识"**。

**Function Calling（工具调用）**，`ai/tool/ShopQueryTool.java`：用 `@Tool`/`@ToolParam` 注解声明 `queryShops(keyword)`、`queryVouchers(shopId)` 两个只读工具，模型自己决定何时调用、传什么参数，拿到真实数据再组织回答。**解决"模型不知道实时数据"**。细节：评分 ÷10、金额分转元——给模型的数据要做单位换算。

**会话记忆**，`ai/memory/RedisChatMemory.java`：key 为 `ai:chat:memory:{conversationId}`，**追加消息用 Lua 脚本原子完成**"读旧→合并→截断最近 20 条→写入并刷新 TTL"（第 42-62 行），避免并发 get-merge-set 竞态丢消息——又一个"Lua 消灭竞态"的实例。只持久化 USER/ASSISTANT/SYSTEM 消息，工具调用消息不入库。

### 8.3 优雅降级：没配 key 也能启动（本章最工程化的部分）

Spring AI 的自动配置对空 api-key 会**启动直接崩溃**。三层解法：

1. **环境后处理器**（`AiFallbackEnvironmentPostProcessor.java`，经 `META-INF/spring.factories` 注册）：环境准备阶段发现 key 为空 → 动态注入 `spring.autoconfigure.exclude` 排除全部 6 个 OpenAI 自动配置 + 标记 `ai.fallback.enabled=true`。
2. **条件装配降级 Bean**（`AiFallbackConfiguration.java`）：`@ConditionalOnProperty(ai.fallback.enabled=true)` 时注册 `FallbackChatModel`/`FallbackEmbeddingModel` 顶替真身。
3. **降级实现的细节智慧**：
   - `FallbackChatModel` 对所有调用返回固定友好文案；
   - `FallbackEmbeddingModel` 返回 **1024 维全 1 向量**——为什么不用零向量？余弦相似度要求范数非零；全 1 向量与真实向量余弦 ≈ 0 < 阈值 0.5，检索自然为空，不会注入错误上下文（`FallbackEmbeddingModel.java:30-43`）；
   - `RagConfig.java:69-72` 检测到降级模型时**跳过快照读写**，防止占位向量"毒化"快照。

### 8.4 RAG 快照持久化：简单问题别用重方案

知识库只有几条向量，内存暴力检索 10 万条也只要 252ms，远低于 LLM 首字延迟——所以**检索永远在内存，快照纯为持久化**（`rag/store/VectorSnapshotRepository.java:19-24` 的设计注释值得全文背诵）。接口抽象 + 双实现：`simple`（本地 JSON 文件）/ `redis`（快照字符串存普通 key `ai:vector:snapshot`，多实例共享，生产推荐）。`app.ai.rag.rebuild=true` 可在知识库更新后强制重建。

### 9.1 目录即架构


亮点：**Element Plus 按需自动导入**由 Vite 插件完成（`vite.config.js:19-20`），组件里直接写 `<el-button>`；**图标白名单注册**约 26 个（`main.js:61-90`），避免 ~300 个图标进首屏包；`setRouter(router)` 把路由实例注入 http 层打破循环依赖（`main.js:99`）。

### 9.2 http.js：一次封装，处处受益（`api/http.js`）

- 请求拦截器：从 `sessionStorage` 取 token 放 `Authorization` 头；
- 响应成功：解包 `Result`，业务失败 reject `errorMsg`；
- 响应失败：**401 优先处理**（清 token、记录 `login_from` 来源页、跳登录），超时/断网/其他状态码各有明确文案。

### 9.3 为什么是 401 驱动而不是路由守卫？（值得细品的设计）

路由表**没有任何 `beforeEach` 守卫**。设计逻辑：

- 大部分页面允许匿名浏览（首页、店铺、笔记详情都能看），只有调鉴权接口时才被 401 拦截跳登录——**按需拦截**；
- 守卫方案要么一刀切拦整页，要么为每个接口维护白名单，都更笨拙；
- 回跳闭环：401 存 `login_from`，登录成功 `Login.vue:79` 取回来源页跳回；
- 配套纪律：未登录场景的组件（如 FootBar 查未读消息红点）**先检查 sessionStorage 有 token 再发请求**（`FootBar.vue:47-49`），否则一个红点接口会把匿名首页劫持到登录页——注释记录了这正是修过的真实 bug。

### 9.4 CSS 五层架构：用工程纪律消灭样式战争

| 层 | 文件 | 职责 |
|---|---|---|
| 1 tokens | `tokens.css` | 唯一设计变量源：品牌橙 `--brand`、玻璃面、文字三级、圆角阴影、z-index |
| 2 base | `base.css` | reset、根字号、排版基线 |
| 3 layout | `layout.css` | `#app` 玻璃外壳、页头、底栏 |
| 4 components | `components.css` | 按钮/卡片/EP 覆写/过渡 |
| 5 page | `page-*.css` | 页面级样式，类名作用域收窄到页面根类 |

三条铁律：① 颜色/圆角/阴影**只许引用 tokens 变量**，禁止字面量；② **不用 `!important`** 抢优先级，靠选择器作用域收窄（EP 覆写用 `body .el-button` 提特异性）；③ 导入顺序即层叠顺序（`main.js:41-53`）。JS 侧需要颜色时从 `utils/colors.js` 取镜像值。

**经典坑**：`#app` 带 `backdrop-filter`，CSS 规范下它成为内部 `position:fixed` 元素的包含块，fixed 定位被"劫持"。解法：悬浮元素一律 `<Teleport to="body">`（`FootBar.vue:1-6`）。

### 9.5 nginx 分流要点（`frontend/conf/nginx.conf`）

- `/app/` 服务 SPA 产物 + `try_files` 回退入口（支持 history 路由）；
- `/api` **剥离前缀**代理后端，`/api/ai/` **保留前缀**且为流式响应关闭 gzip 与 `proxy_buffering`、超时放宽 300s——SSE 流式接口的关键配置；
- 覆写 `X-Real-IP`/`X-Forwarded-For` 防客户端伪造（后端限流只信任 nginx 注入的 IP）。

## 第 10 章：工程素养与面试考点速查

### 10.1 本项目反复出现的设计模式

| 模式 | 出现处 |
|---|---|
| Lua 原子化消灭竞态 | seckill.lua、unlock.lua、RedisChatMemory 追加消息 |
| 事务提交后再做副作用（afterCommit） | 发券写 Redis、删笔记清缓存 |
| 幂等设计 | 唯一索引 + DuplicateKeyException、Stream at-least-once + DB 查重 |
| 降级优先于崩溃 | AI fallback 三层机制、缓存重建超时降级查库、限流 Redis 故障放行 |
| 快速拒绝 + 最终兜底 | 秒杀 Lua（性能）+ DB 锁/唯一索引（正确性） |
| 单一数据源 + 镜像 | tokens.css ↔ colors.js；sessionStorage ↔ Pinia store |

### 10.2 面试考点索引

1. **缓存三兄弟**：穿透（空值缓存/布隆过滤器）、击穿（互斥锁/逻辑过期）、雪崩（TTL 随机化）——本项目三模式都有生产级实现可讲。
2. **秒杀系统设计**：讲清"三道防线"——Lua 原子预扣（快拒）、Stream 异步削峰（可靠投递）、DB 乐观锁+唯一索引（兜底）。以及为什么每一道都不能省。
3. **分布式锁**：SET NX EX 的持有者标识问题 → Lua 原子释放 → Redisson 看门狗与可重入。
4. **ThreadLocal**：原理、线程池复用的内存泄漏/串号风险、remove 时机。
5. **Feed 流**：推/拉/推拉结合的场景权衡；滚动分页如何解决动态数据的重复漏读。
6. **幂等与事务**：消息至少一次投递 + 消费端幂等；本地事务与缓存副作用的次序（afterCommit）。
7. **全局唯一 ID**：雪花算法结构、时钟回拨、按天分段的统计红利。
8. **RAG/Function Calling**：边界划分（私有静态知识 vs 实时动态数据）、降级设计。
